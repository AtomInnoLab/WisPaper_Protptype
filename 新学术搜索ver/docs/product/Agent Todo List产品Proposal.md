# Agent Todo List 产品 Proposal

> 让 Agent 的长任务变得可理解、可干预、可恢复  
> WisPaper 产品提案 · MVP · 2026-08-14

## 1. 执行摘要

WisPaper Agent 已能够把研究目标拆解为执行计划，并调用搜索、阅读、分析与实验工具。但当前计划更接近过程展示：用户能够看到 Agent 正在做什么，却难以修改后续步骤、处理阻塞或从失败位置继续。

建议为 Agent 增加原生 Todo List，将一次 Agent 任务拆成一组有状态、有依赖、有产物的执行项。用户可以在开始前确认计划，在执行中查看进度和处理需要确认的事项，在任务中断后从未完成项继续。

Todo List 的产品定位不是通用任务管理器，而是：

> 用户与 Agent 之间的可执行任务契约。

MVP 需要验证：当 Agent 的执行计划可以被查看、调整和恢复时，用户是否更愿意启动复杂任务，并能够更少地因过程不透明而中止任务。

## 2. 背景与问题

当前 Agent 长任务存在四类问题：

- **过程不透明**：用户只看到“正在思考”或阶段性日志，不清楚还剩多少工作。
- **计划不可控**：Agent 拆解出的步骤无法在执行前调整，用户只能取消后重新描述任务。
- **阻塞难处理**：遇到文件缺失、权限不足、选项冲突或需要用户判断时，没有统一的待处理入口。
- **中断难恢复**：刷新页面、任务失败或余额不足后，用户难以从上次完成的位置继续。

这些问题在文献综述、论文复现、批量筛选和长期调研中尤为明显，因为任务通常包含多个工具调用和相互依赖的步骤。

## 3. 产品目标

### 3.1 用户价值

- 在任务开始前理解 Agent 准备如何执行。
- 知道当前步骤、剩余步骤和阻塞原因。
- 可以修改尚未执行的任务，而不必重启整个对话。
- 在需要判断时明确收到待办，并将结果交还 Agent 继续执行。
- 任务失败或退出后可以从断点恢复。

### 3.2 产品价值

- 提升复杂 Agent 任务的启动率和完成率。
- 减少因过程不透明产生的取消、重复提交和客服反馈。
- 为 Credits 消耗、Agent 产物和任务失败提供清晰的归因单位。
- 为后续科研画布、Project 和多人协作提供统一的任务对象。

## 4. 产品定位与边界

| 维度 | 定义 |
|---|---|
| 一句话定位 | Agent 为完成当前研究目标而维护的动态执行清单。 |
| 核心用户 | 使用 Agent 完成多步骤调研、综述、复现或分析任务的研究者。 |
| 创建者 | Agent 自动生成，用户可补充或修改未执行项。 |
| 生命周期 | 隶属于一次 Agent 任务，从计划生成持续到任务结束或取消。 |
| 与聊天的关系 | 聊天用于沟通目标和结果，Todo List 用于呈现和控制执行过程。 |
| 与 Project 的关系 | Todo 可关联 Project，但 MVP 不承担跨项目的通用任务管理。 |

Todo List 暂不替代日历、提醒、看板或个人效率工具，也不作为新的一级菜单。

## 5. 核心产品模型

### 5.1 Todo 类型

| 类型 | 含义 | 示例 |
|---|---|---|
| Agent 任务 | 由 Agent 调用工具并自动完成 | 检索近五年关于长期记忆的论文 |
| 用户确认 | Agent 需要用户做选择或批准 | 确认纳入哪些数据库 |
| 用户任务 | 必须由用户提供材料或完成操作 | 上传实验配置文件 |
| 检查点 | 阶段结束后对结果进行确认 | 确认证据表后继续生成综述 |

### 5.2 Todo 状态

| 状态 | 说明 |
|---|---|
| 待执行 | 已进入计划，尚未开始 |
| 进行中 | Agent 当前正在执行 |
| 等待确认 | 等待用户选择、授权或补充信息 |
| 已阻塞 | 因依赖、权限、文件或环境问题无法继续 |
| 已完成 | 已产生符合要求的结果或产物 |
| 已跳过 | 用户或 Agent 明确跳过，不再执行 |
| 执行失败 | 已尝试但未成功，需要重试、修改或终止 |

状态必须表达真实结果。工具调用已发起但未返回成功时，不能标记为“已完成”。

### 5.3 Todo 信息

每个 Todo 至少包含：

- 标题与简短目标；
- 类型、状态和执行顺序；
- 前置依赖；
- 当前动作或阻塞原因；
- 创建来源：初始计划、用户添加或 Agent 建议新增；
- 关联输入、论文、文件和工具；
- 完成后生成的结果或产物；
- 开始、完成和最近更新时间。

MVP 最多展示两级结构：阶段与 Todo。避免无限层级导致计划难以阅读。

## 6. 核心交互

### 6.1 计划生成与确认

1. 用户提交研究目标。
2. Agent 生成 3-8 个 Todo，并说明关键依赖。
3. 简单任务可直接开始；复杂、高成本或包含外部操作的任务先进入计划确认。
4. 用户可以修改标题、补充 Todo、删除非必要项或调整尚未执行项的顺序。
5. 用户确认后，Agent 从第一个可执行 Todo 开始。

### 6.2 执行过程

- Todo List 常驻 Agent 工作界面的“执行计划”区域。
- 默认折叠已完成项，突出当前项与需要用户处理的事项。
- 顶部显示整体摘要，例如“3/7 已完成”“1 项等待确认”。
- 点击 Todo 可查看使用的输入、运行信息、证据和输出产物。
- Agent 完成一项后自动更新状态，并继续执行满足依赖的下一项。

### 6.3 用户干预

| 用户操作 | 系统处理 |
|---|---|
| 修改待执行项 | 保存修改，并检查是否影响后续依赖 |
| 调整顺序 | 仅允许在依赖关系成立时调整 |
| 新增 Todo | 加入当前计划，Agent 判断依赖和执行位置 |
| 跳过 Todo | 展示对后续任务的影响，确认后跳过 |
| 暂停任务 | 当前安全节点结束后暂停，不启动下一项 |
| 重试失败项 | 保留上次错误信息，从该项重新执行 |
| 回答确认项 | 保存用户选择，Agent 自动恢复执行 |

正在执行的 Todo 不允许直接删除。若修改会扩大任务范围、增加明显成本或使已有产物失效，Agent 必须先展示变更影响并获得用户确认。

### 6.4 动态规划

Agent 在执行中发现新问题时，可以建议新增 Todo，但不能静默扩大任务范围。

新增项应标记为“Agent 建议”，并说明：

- 为什么需要新增；
- 是否阻塞原计划；
- 对预计时间和 Credits 的影响；
- 用户可以接受、修改或拒绝。

## 7. 界面建议

### 7.1 启动页

启动页不展示空 Todo List。用户提交目标后，在 Agent 生成计划时显示结构化计划卡片。

### 7.2 Agent 工作界面

- 右侧“执行计划”作为 Todo List 的固定容器。
- 收起状态显示完成数量、当前步骤和异常数量。
- 展开后按“正在进行、需要处理、待执行、已完成”组织内容。
- 当前 Todo 使用蓝色强调；等待用户使用琥珀色；失败使用红色；完成使用中性勾选状态。
- Todo 详情与任务文件、论文和运行环境互相链接，不重复展示完整内容。

### 7.3 对话区

对话只保留关键事件：计划已生成、需要确认、阶段完成、任务失败和最终结果。高频进度更新留在 Todo List，避免对话被运行日志淹没。

### 7.4 移动端

Todo List 通过全屏抽屉展示。顶部保留当前 Todo 和需要用户处理的事项，编辑与排序操作降级为菜单。

## 8. Agent 行为规则

1. Agent 必须先明确目标，再生成 Todo，不把推理草稿作为 Todo。
2. Todo 使用用户能够判断结果的动作描述，例如“筛选核心论文”，避免“继续思考”。
3. 每个 Todo 应有可判断的完成条件。
4. Agent 只能自动修改未执行项，且需要留下变更记录。
5. 涉及付费、发布、删除、外部写入或明显扩大范围的操作必须等待用户确认。
6. 发生失败时保留已完成项与产物，不回滚整个任务。
7. 用户返回任务时，Agent先读取 Todo 状态和已有产物，再决定从哪里继续。
8. 最终回答需要引用已完成 Todo 的核心产物，并说明未完成或跳过的事项。

## 9. MVP 范围

### P0

- Agent 自动生成 Todo List。
- 阶段与 Todo 两级结构。
- 待执行、进行中、等待确认、已阻塞、已完成、已跳过、执行失败状态。
- 当前进度、整体完成数量和阻塞提示。
- 编辑、新增、排序、跳过、暂停、继续和失败重试。
- Todo 与文件、论文、工具结果和最终产物关联。
- 页面刷新或退出后的任务恢复。
- 关键变更记录与基础操作日志。

### P1

- Agent 建议新增 Todo，并展示时间和 Credits 影响。
- Project 与科研画布中的任务引用。
- Todo 模板和常用研究计划复用。
- 多个无依赖 Todo 的并行执行。
- 完成条件和阶段验收配置。

### 暂不纳入

- 全局个人待办中心；
- 日历、提醒、重复任务；
- 复杂甘特图与完整看板；
- 多人实时编辑和任务分配；
- 用户自定义 Agent 编排图；
- 无限层级子任务。

## 10. 验证方案与成功指标

### 10.1 关键假设

- **H1**：计划可见能提高用户启动复杂 Agent 任务的意愿。
- **H2**：可干预的 Todo 能降低取消后重新提交任务的比例。
- **H3**：等待确认和断点恢复能提高长任务最终完成率。
- **H4**：用户能够理解 Todo 状态，并认为它代表真实执行进展。

### 10.2 指标

| 目标 | 核心指标 |
|---|---|
| 计划理解 | 计划确认率、计划编辑率、首次确认耗时 |
| 任务完成 | 含 3 个以上 Todo 的任务完成率 |
| 用户控制 | 跳过、修改、暂停、继续和确认操作的成功率 |
| 恢复能力 | 中断任务恢复率、恢复后的最终完成率 |
| 失败处理 | 阻塞项解决率、失败项重试成功率 |
| 体验质量 | 因“看不懂进度”导致的取消率和负向反馈率 |

建议先针对文献综述、论文复现和批量论文筛选三类任务进行测试，对比现有线性执行计划与可交互 Todo List 的完成率和用户信任度。

## 11. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 计划制造虚假确定性 | Agent 生成的计划看似完整，但执行中频繁变化 | 明确计划可动态调整，并展示变更原因 |
| 用户过度干预 | 频繁调整导致依赖混乱或任务无法完成 | 限制进行中项编辑，对有影响的修改先做校验 |
| 信息过载 | 长列表占据界面并与聊天重复 | 默认突出当前项、异常项，折叠完成项和运行细节 |
| 状态不可信 | Agent 提前标记完成或进度长期不更新 | 状态与工具结果绑定，区分运行、成功和失败 |
| 任务范围膨胀 | Agent 不断新增步骤导致时间与费用失控 | 新增 Todo 默认需要用户接受，并展示影响 |
| 与 Project 重叠 | 用户不清楚 Agent Todo 与项目任务的区别 | MVP Todo 仅属于单次 Agent 任务，Project 只做引用 |

## 12. 推进建议

| 阶段 | 周期 | 交付物 |
|---|---|---|
| 交互原型 | 1-2 周 | 计划确认、执行更新、用户确认、失败恢复四条核心路径 |
| MVP 开发 | 3-5 周 | Todo 数据模型、Agent 状态同步、基础编辑与恢复 |
| 封闭测试 | 3-4 周 | 三类真实研究任务、行为数据和用户访谈 |
| 评估 | 1 周 | Go / Iterate / Stop 结论及后续与 Project 的整合范围 |

## 13. 本次评审需要确认

1. Todo List 是否只服务单次 Agent 任务，暂不扩展为全局任务中心？
2. 哪些任务必须先确认计划，哪些任务可以自动开始？
3. 运行中允许用户修改到什么程度，是否需要统一的重新规划确认？
4. 等待用户确认时，Agent 任务是否暂停计时和资源占用？
5. MVP 是否需要并行 Todo，还是先按依赖顺序串行执行？
6. Todo 是否在首个版本中同步到 Project 和科研画布？

## 推荐下一步

先制作包含以下四种状态的可交互原型：

1. Agent 生成计划，用户确认并调整；
2. Agent 执行中自动更新 Todo；
3. 某个 Todo 等待用户确认或发生阻塞；
4. 用户退出后返回，并从失败或未完成项继续。

优先验证用户是否把 Todo List 理解为真实执行状态，以及它是否能减少取消后重新创建任务的行为。在这两个假设成立前，不建议扩展到全局任务中心、日历或复杂协作。
